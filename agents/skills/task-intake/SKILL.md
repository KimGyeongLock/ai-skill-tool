# Task Intake
1. **입력 확인:** 공식 README, 제공 코드, 데이터 파일, 예제, 제출 규격, 실행/시간 조건을 직접 열어 확인한다. 키트 README와 구별한다.
2. **조건 구조화:** 하드 제약(절대 위반 불가), 소프트 선호(개선 대상), 목적함수(무엇을 최소/최대화하며 어떤 식으로 계산?), 제출 형식, 운영상 우선순위를 분리한다. 명세가 점수나 목적함수를 언급하지 않으면 그 사실도 적는다.
3. **실무 질문:** 업무 결과를 실질적으로 바꾸는 질문 2~3개를 우선 제시한다. 예: 성공의 정의, 동률 처리, 예외, 누락 데이터, 우선순위, 비용/정확도 트레이드오프. 실제 답을 받으면 추가로 필요한 질문을 할 수 있다. 담당자 답변을 지어내지 않는다.
4. **가정 기록:** 확인한 사실(근거 위치), 합리적 잠정 정책(이유/영향), 아직 막힌 조건을 분리한다. 구현에 영향을 주는 미확정 조건이면 먼저 확인한다.
5. **실행 계획:** 입력→주요 처리→결과 제출이라는 전체 그림, 최소 실행 가능한 수직 흐름, 기능 단계별 성공 기준과 테스트를 만든다. 평가 지표가 있는 과제라면 기준선을 확보한 후 최적화와 재검증을 계획에 반드시 넣는다.
6. **출력:** 먼저 한두 줄 결론, 이어서 `[x] 확정된 요구`, `[?] 미확정 질문`, `성공 지표/제약`, `구현 우선순위`, `검증 계획` 순서로 짧은 체크리스트 또는 표를 출력한다. 각 항목에 공식 근거를 붙인다. 목표가 없거나 질문이 불필요하면 억지로 만들지 않는다.

분석 단계에서 코드와 설정을 변경하지 않는다. 질문이 필요 없다면 만들지 않는다. 과제 전체 파일을 무작정 모델 입력에 출력하지 않는다.
