# Task Verify — 이 파일만 읽어도 전체 최종 검증을 수행

**사용자가 `task-verify 읽고 검증해줘`라고만 말해도** 아래 절차를 직접 수행한다. 앞 단계의 채팅/작업 기록을 참고하되, 공식 과제 README와 **최종 제출물**을 기준으로 독립 확인한다.
1. 실제 공식 README/지시서의 요구와 제출 형식을 먼저 다시 읽는다. 보조 키트의 안내를 명세로 사용하지 않는다.
2. **추출:** 중요한 입력, 행/파일/조항과 근거를 확인한다. 계산이 있다면 핵심 분자·분모·중간값·단위와 경계값을 확인한다.
3. **실제 실행:** 주요 사용 경로, 정상·경계·오류/누락 입력을 검사한다. 실행한 명령과 관찰된 값만 기록한다. 테스트가 0개거나 전부 skip이면 통과가 아니다.
4. **독립 검산:** 다른 함수/쿼리, 표본 수작업 대조, 불변식, 역산 등의 별도 방법을 이용한다. 같은 구현의 재실행은 독립 검산이 아니다.
5. **제약 검증:** 모든 하드 제약과 제출 규격의 충족을 확인한다. 목적함수가 있는 경우 실제 지표 값과 유효성을 확인하고 개선 전후가 **동일 조건**인지 대조한다.
6. **최종 보고:** 요구사항별 `확인됨/실패/미확인`, 실제 증거, 막는 문제, 개선 가능성 및 한계. 검산되지 않은 결과를 확정으로 표현하지 않는다.

## 화면에 보여줄 결과 (간결한 체크리스트)

1. **결론:** 제출 가능 여부와 가장 큰 문제 1~2개를 첫 줄에 표시한다.
2. **필수 요구사항 체크:** 요구마다 `[x] 확인됨` / `[!] 실패` / `[?] 미확인`으로 표시하고 실제 근거를 붙인다. 항목이 많다면 아래 표로 요약한다.

   | 요구사항 | 상태 | 실행/입력 근거·핵심 중간값 | 조치 |
   |---|---|---|---|
   | (실제 확인한 항목만) | 확인됨/실패/미확인 | 실제 관찰한 값만 | 필요한 조치 |

3. **경계 및 실패 사례:** 정상/경계/누락/예외 테스트의 실행 여부와 결과를 짧게 표시한다.
4. **독립 검산:** 구현과 다른 계산·판정 경로, 비교 값 및 차이를 짧게 제시한다. 불가능했다면 `[?] 미검증`이라고 쓴다.
5. **목적함수와 제약:** 해당될 때에만 기준선/최종 지표/증감, 필수 제약 위반 수, 동일 입력 비교 여부를 표시한다. 목적함수가 없다면 `해당 없음`이라고 쓴다.
6. **최종 판정:** 제출 차단 문제, 남은 한계, 지금 할 가장 중요한 다음 행동 1~2개를 남긴다.

형식보다 **실제 검증 증거**가 우선이며, 출력이 길어지면 자세한 로그는 파일/명령 위치만 알려준다. 체크 표시를 실행 증거 없이 채우지 않는다.

`검증 완료`라고 말하려면 수행된 테스트와 적절한 독립 근거가 있어야 한다. 외부 전송이나 감독 설정 변경을 해서는 안 된다.

## 코드 및 아키텍처 검토
- 프로젝트에 실제 존재하는 프론트엔드, 백엔드, DB, Docker Compose 및 설정 파일을 확인한다. 존재하지 않는 구성 요소는 검사 대상으로 가정하지 않는다.
- 공식 README의 필수 요구사항을 실제 파일, 함수, API 및 화면과 연결한다.
- 핵심 로직, 데이터 흐름, 실행 상태, 예외 처리와 서비스 연결 상태를 확인한다.
- 성능 및 품질 개선 가능 지점을 실제 코드, 실행 결과 및 측정값에 근거해 식별한다.
- 문제점은 중요도순 체크리스트로 정리하고 파일 위치, 근거, 영향 및 수정 우선순위를 표시한다.
- 검토만 요청받은 경우 코드를 수정하지 않는다. 확인하지 못한 내용은 미확인으로 표시한다.
